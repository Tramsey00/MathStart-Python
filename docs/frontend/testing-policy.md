# Проверки на текущем этапе переноса

Решение пользователя от 25.10.2026. Имеет приоритет над прежним «коротким»
профилем, таблицами приёмки и перечислениями команд в карточках.

## Сейчас: автоматические прогоны выключены

Для обычных правок UI, CSS, React-компонентов, текстов и Markdown — **0 тестовых
прогонов по умолчанию**. Не запускать по собственной инициативе npm tests,
typecheck, Playwright, check:dev, verify_repo, source/docs/preservation gates,
полный backend либо новый «маленький smoke». Отдельное поручение пользователя
на конкретную проверку разрешает её scope, а не весь связанный набор.
Запрет проверок нельзя обходить словами «быстрый», «targeted», «smoke» или
«на всякий случай». Не создавать новый каскад взамен удалённого.

Рабочий цикл: реализация → HMR → просмотр/приёмка пользователем. Сборка нужна
для отдельно порученной подготовки готовой версии. Dev startup и сборка не
должны вызывать тестовые suites. Доменные валидаторы и штатные integrity guards
публикации остаются частью приложения; их наличие не разрешает отдельный QA.

## Перенос классов MS-T003–MS-T008 — решение 08.11.2026

Задача агента — перенос по принятому стандарту, сверка с исходником и передача
пользователю для ручного просмотра материала и интерактивов. Автоматические
прогоны и новые QA-скрипты не входят в перенос. Не добавлять тесты на каждый урок,
не запускать browser automation, smoke или gates для завершения карточки.
Непроверенное вручную отметить явно; статус проверок — NOT_RUN_BY_USER_REQUEST.
Статическое review и ручная человеческая приёмка сохраняются раздельно.
Штатная подготовка новых Content inputs выполняется по инструкции с планами/guards;
не повторять её или release build после каждой UI-правки. Валидаторы приложения
не отключать. Отдельно порученная в будущем проверка имеет только свой scope.

## Взаимное ручное ревью уроков

Коллеги могут параллельно смотреть PR друг друга. Автор передаёт ссылку на PR,
полный source SHA для запуска, список canonical URL и несколько мест для более
внимательного просмотра. Если пакет ревью добавлен отдельным коммитом, автор
явно указывает SHA для checkout и подготовки Content и даёт ссылку на пакет
в коммите с документацией.

### Получение исходников на Windows

Для первого просмотра рекомендуется отдельный полный clone с собственной
локальной конфигурацией и PostgreSQL. Дамп БД, `var/`, настройки и готовая сборка
автора не нужны. Пример для PowerShell из родительского каталога. Укажите номер
PR, полный SHA из пакета и новое короткое имя папки.

```powershell
$prNumber = Read-Host 'Номер PR'
$sourceSha = Read-Host 'Полный source SHA для запуска'
git clone --no-checkout -c http.version=HTTP/1.1 -c core.longpaths=true -c core.autocrlf=false https://github.com/Tramsey00/MathStart-Python.git MathStart-review
Set-Location MathStart-review
git fetch origin "refs/pull/$prNumber/head"
git switch --detach $sourceSha
git rev-parse HEAD
```

При ошибке команды или несовпадении HEAD с указанным SHA остановитесь и уточните
источник у автора.

### Подготовка локальной публикации

Соблюдайте [требования host-dev](../local-development-host.md#требования) и
выполните locked установку зависимостей из [шага 1](../local-development-host.md#1-clone-и-locked-установка)
в этой копии. Освободите порты по инструкции. Ниже команды первой установки.
Codex может подготовить окружение по поручению, а каждый план просматривает
и подтверждает человек.

1. Выполните `& .\.venv\Scripts\python.exe scripts/team_local.py init`, затем
   `& .\.venv\Scripts\python.exe scripts/team_local.py schema-preview`.
   Просмотрите `var/local/team/schema.json`. Для применения замените
   `$schemaSha256` на точный SHA256 просмотренного плана в команде
   `& .\.venv\Scripts\python.exe scripts/team_local.py schema-apply --reviewed-plan-sha256 $schemaSha256`.
2. Выполните `& .\.venv\Scripts\python.exe scripts/team_local.py content`.
   Отдельно просмотрите `var/local/team/publication.json`. Для публикации
   замените `$publicationSha256` на точный SHA256 этого плана в команде
   `& .\.venv\Scripts\python.exe scripts/team_local.py publish --reviewed-plan-sha256 $publicationSha256`.
3. Перед просмотром сверьте `git rev-parse HEAD` и `Prepared source SHA` из
   вывода подготовки с SHA для запуска. Сверьте `release_id` плана с активным
   release в БД этой копии и убедитесь, что его публикация завершилась с
   `COMPLETE`. Статус можно прочитать через `backend.content.publish status`
   с настройками этой БД и `--operation-id` из результата публикации.
   Затем запустите `npm.cmd --prefix frontend run dev:host`, дождитесь
   готовности и откройте canonical URL на `http://127.0.0.1:8131`.

Для ручного просмотра опубликованного release можно использовать
[собранную FastAPI-версию без Vite](../local-development-host.md#собранная-fastapi-версия-без-vite).
Этот режим подходит, если нужно проверить собранный CSS или Vite мешает открыть страницу.

После исправлений можно использовать ту же копию. Для следующего PR используйте
её только при наличии штатного пути обновления публикации и ожидаемого плана.
Для существующей БД следуйте [порядку обновления host-dev](../local-development-host.md#после-git-pull),
а при отсутствии подходящего пути подготовьте свежую копию. Само переключение
ветки не обновляет опубликованный Content. Перед повторным просмотром снова
сверьте исходники и публикацию.

### Просмотр и результат

- Быстро пройдите все URL из списка. Сверьте адрес и заголовок, пролистайте
  страницу в поисках крупных пропусков и визуальных поломок, попробуйте один-два
  характерных клика. Подробнее смотрите навигацию, мобильный вид, формулы, SVG
  и интерактивы на выборке и в местах, отмеченных автором.
- К исходнику обращайтесь при конкретном подозрении. Посимвольная сверка,
  раскрытие всех решений и отчёт на каждый урок в этот объём не входят.
  Автоматические QA-прогоны не запускайте.
- Оставьте один комментарий в PR с проверенным SHA, release, охватом и
  замечаниями в формате «URL — проблема — как воспроизвести». Если страницу
  открыть не удалось, укажите URL и причину блокировки.
- После исправлений тот же коллега смотрит затронутые страницы на новом SHA.
  В конце Руслан смотрит выборку и исправленные места, принимает результат
  и отдельно решает вопрос о merge.

## Что изменено

- `test:lesson` удалён: он запускал почти весь frontend suite и не был коротким.
- `scripts/verify_lesson.py` удалён: каскад frontend/typecheck/backend/schema/
  source gates больше не является входом повседневной работы.

- Все GitHub workflows имеют только ручной workflow_dispatch. Push/PR
  не запускают frontend, backend, browser или документационные прогоны.
- Существующие test-файлы сохранены для будущей отдельно назначенной проверки.
  Их не нужно читать или запускать при каждой UI-правке.

## Только по отдельному поручению

Полный frontend entry — `npm --prefix frontend run test:full`.
Typecheck, `check:dev`, browser, backend и release commands также ручные.
Полные entry points сохраняют assertions, fail/skip/timeout rejection и receipts;
их результат нельзя получать подменой тестов пустым PASS.

Возврат автоматизации — отдельное решение пользователя. В MS-T009/MS-T011
пересмотреть нужные проверки по фактическим функциям; не восстанавливать прежний
массовый набор автоматически. Старые списки и отчёты доступны в Git и не дают
разрешения повторять прогоны. Текущая пометка без запуска — NOT_RUN_BY_USER_REQUEST.
Результаты 24.10.2026 остаются историей того candidate и не проверяют новые правки.
