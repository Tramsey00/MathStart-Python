# MathStart: правила работы coding-агента

## Задание и источники

Один исполнитель, одно явно порученное задание. Не начинай следующую карточку
автоматически. Новые функции, UI и игровые механики требуют отдельного поручения
и принятых решений. Старые ТЗ, аудиты, source cards и персональные очереди
не задают текущую работу; не восстанавливай старые миграционные worktree.

Для порученной карточки открой [единую очередь](docs/tasks/INDEX.md) и саму
карточку `skills/tasks/.../SKILL.md` по ссылке из очереди. Там указаны статус,
зависимости, scope и приёмка. Затем читай только нужные разделы
[архитектуры](ARCHITECTURE.md) и источники карточки. Используй task skills явно;
не полагайся на их автообнаружение.

- Для доменных изменений открой [карту действующих контрактов](specs/current-contracts.md)
  и нужные контракты и продуктовые требования по её ссылкам. Соблюдай границы
  модульного монолита и владение данными. Изменение семантики упражнений или
  прогресса требует спецификации, проверок и архитектурного ревью. Версионируй
  LLM-промпты; обычные тесты не обращаются к живому LLM.
- Для UI открой [общий UI-контракт](docs/ux/shared-ui-contract.md). Сохраняй
  утверждённый дизайн главной, каталога и урока, палитру и шрифты. Не вводи
  новый UI kit и не используй I02/I03 как образец.
- Для урока открой [стандарт переноса](docs/frontend/lesson-migration.md) и
  [общий skill](skills/lesson-migration/SKILL.md). Применяй раздел «Действующие
  решения пользователя»; фиксируй согласованные отступления от сохранения
  источника в карточке. Старые preservation notes не отменяют этих решений.
- Для локального запуска, HMR и обновления открой
  [руководство по разработке](docs/local-development.md): основной путь —
  Windows host-dev (Vite/FastAPI на хосте, PostgreSQL в Docker). Работай в обычной
  папке проекта; отдельный clone для ежедневной работы не требуется.
  Полный Docker Compose — альтернативный режим. Используй общий origin и штатный HMR.
  Не запускай отдельные prototype servers и release build после каждой UI-правки.
  Для статуса и контроля запуска из clone смотри [MS-T002A](skills/tasks/t002a-team-local-start/SKILL.md).
- Для release или восстановления открой соответственно
  [регламент выпуска](deploy/RELEASE.md) или [регламент восстановления](deploy/RECOVERY.md).
  Для принятой истории смотри [журнал сопровождения](docs/maintenance.md).
- При явно необходимом legacy-сравнении используй только
  [отдельный pinned oracle](docs/legacy-oracle.md). Не устанавливай Django/DRF
  в target и не используй исходную Django DB или защищённый acceptance stack для тестов.

При расхождении источников укажи его и следуй явно установленному приоритету;
если приоритет не определён, не меняй политику догадкой.

## Git и реализация

В начале проверь Git root, ветку, HEAD, dirty tree, remote и отношение к
`origin/main`. Сохраняй чужие правки. Работай в ветке задания основного checkout.
Не редактируй и не коммить в `main`; запрещены `reset --hard`, принудительные
checkout и push, автоматический merge.

**Bootstrap:** MS-T001, MS-T002 и MS-T002A используют общую `ui/ux` без
отдельных Issue и веток; продолжай существующий PR. Порядок приёмки, решения о
merge и проверки clone опубликованного main до MS-T003 — в
[очереди](docs/tasks/INDEX.md#bootstrap-и-работа-команды) и карточке MS-T002A.
Production deploy в bootstrap не входит.

**С MS-T003:** для каждого порученного задания — GitHub Issue со scope,
критериями приёмки и ссылками на результат → отдельная ветка от актуального
`origin/main` после fetch → PR со ссылкой на Issue. Пример ветки:
`ms-t003-grade-5`; без `codex/` и `/codex`. Продолжай существующие Issue,
ветку и PR без дублей. Не создавай Issue на всю очередь и не закрывай их
автоматически. Если GitHub недоступен, явно сообщи об этом.

Перед правками проверь реальные imports и build inputs. Выбирай порядок работ
по зависимостям и держи изменения в рамках задания. Сохраняй данные, авторский контент, медиа, формулы, URL, якоря и
контракты. Не ослабляй проверки ради PASS. Не допускай необъяснённых изменений
или удалений сохраняемых материалов; для выведенных файлов нужна пофайловая
карта. Исторические receipts и подтверждения приёмки не переписывай.

- Только Progress меняет долгосрочное знание через валидированные ProgressEvent.
  Чтение, XP/награды, Tutor, Analyzer, frontend и LLM не увеличивают mastery напрямую.
- Startup не делает DDL, bootstrap, content/operator seed или публикацию.
  Изменения схемы — через reviewed Alembic migrations с fresh/upgrade проверками
  PostgreSQL; применённую историю миграций не редактируй.
- Секреты, cookies и персональные данные не попадают в Git и отчёты.
  Ответы и ключи проверки серверные до явного reveal по контракту Assessment.

## Проверки и завершение

**При текущей UI-миграции не запускай автоматические проверки и smoke по своей
инициативе.** HMR их не требует. Следуй [политике проверок](docs/frontend/testing-policy.md):
она приоритетнее старых checklists и команд в карточках. Если прогоны запрещены,
укажи `NOT_RUN_BY_USER_REQUEST`; не запрашивай ненужный QA после каждой правки.
Не отключай доменные guards и валидаторы под видом отключения прогонов.

Только для отдельно порученных проверок открой
[verification skill](skills/verification/SKILL.md) и, для runtime,
[руководство по проверкам](docs/target-runtime.md). Соблюдай порученный scope.
Результаты старого кандидата не подтверждают новый.

Реализация → самопроверка кода → PR → отдельное ревью → исправления и необходимая
перепроверка → человеческая приёмка → решение пользователя о merge.
Самопроверка не заменяет отдельное ревью; PASS, PR и merge не означают приёмку.
Фиксируй статусы раздельно. Архитектурные и production/provider/security решения
принимает человек.

Для существенной работы оставь в карточке или PR исходный и проверенный
SHA/tree, краткое описание изменений, команды и результаты, ограничения,
замечания ревью и исправления. После передачи результата остановись.
