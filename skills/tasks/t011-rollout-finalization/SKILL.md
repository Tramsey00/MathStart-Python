## Адреса и перенаправления — уточнение 18.11.2026

### Принятое поведение

«Прямой переход» означает, что href/Link/навигация уже содержит действующий canonical URL. Пользователь нажимает тему и сразу получает новый React-урок. Это не скрытый redirect/rewrite старого адреса и не повторное вычисление номера темы. Клиентская навигация React между новыми страницами допустима.

| Вид адреса или действия | Результат |
| --- | --- |
| Новый canonical урок, например /materials/5-math-1 | Прямой GET 200 с новым уроком; корректны reload, Back и anchors |
| Ссылка из каталога, урока, меню, поиска или footer | Уже содержит новый canonical URL; нет промежуточного обращения к старому |
| Выведенный старый slug урока, например /5-klass-chislovye-i-bukvennye-vyrazheniya/ | HTTP 404 и общая 404; нет старого UI, 301/302/307/308, meta-refresh или JS-перехода |
| Выведенная legacy категория, старый каталог или префикс /mathstart/… | После точной инвентаризации и замены внутренних ссылок — 404; не сохранять как алиас нового каталога |
| Неизвестная публичная страница | 404; не отправлять автоматически на главную/каталог |
| Действующие /, /materials, auth, account и информационные страницы | Сохранить их реальные canonical URLs; не считать адрес старым только из-за формы slug |
| Вход/выход и безопасный возврат к выбранной странице | Сохранить существующий authentication flow; return проверяется и ведёт прямо на действующий новый адрес |
| HTTP → HTTPS и утверждённая нормализация origin на production edge | Технические redirects сохраняются; production-конфигурацию не менять без отдельного поручения |
| CSS, изображения, шрифты, API и immutable release URLs | Не выводить вместе со страницами автоматически; анализ потребителей и соответствующих контрактов обязателен |

Цена решения: прежние внешние ссылки и закладки на выведенные учебные URL перестанут вести на урок и получат 404. Это намеренный отказ от legacy URL-совместимости по решению Руслана. Нельзя вместо этого оставлять старую страницу или незаметно возвращать redirect.

### Карта адресов до удаления

В одной актуальной сводке карточки/PR составить карту: старый path → источник/тип → действующая новая цель → внутренние потребители → действие вывода → фактический результат/непроверенное. Учитывать:
- slug уроков, /category/… и старые class/subject pages, /mathstart/…, служебные старые aliases из source registry и автоматически образуемые lesson aliases;
- Unicode/percent-encoded пути, фактически поддерживаемые slash-варианты и query/anchors. Не придумывать новые aliases ради покрытия;
- все 263 назначения из material-routes.json/inventory; заранее сверить коллизии старого path с действующим canonical;
- каталог/поиск, общие шапку/footer, соседние темы, хлебные крошки, content.json/body.html там, где они реально потребляются, sitemap/canonical tags;
- robots, fallback маршруты и серверные/клиентские redirect/rewrite rules, которые могут вернуть старый UI после удаления видимой ссылки.

Сначала заменить внутренние потребители, затем вывести старые публичные маршруты и aliases. Существующие номера тем, identity/IDs, якоря и учебное содержание не менять. Если старый anchor получает новую цель, явно отразить mapping при замене ссылки; fragment не считать данными, которые сервер обязательно получает. При коллизии или неоднозначной цели не удалять адрес догадкой, указать конкретный blocker.

### Фактическое удаление старых страниц

Старые опубликованные уроки и заменённые страницы реально выводятся из обслуживаемого набора. Недостаточно скрыть ссылку, показать 404-компонент поверх прежнего урока или отправить пользователя на /404.

- Удалить их публичные route/page entries, старые HTML-представления/adapters и соответствующие legacy redirect/alias entries из новых source/build inputs. Если старый ContentPage всё ещё публикуется, штатно снять старое представление с публикации, сохранив identity/ID и пользовательские связи новой canonical темы. Не удалять общую сущность темы, которую использует новый урок.
- Новый действующий immutable release/public artifact не содержит обслуживаемой старой страницы. Старый адрес отсутствует в его публичной карте; сервер возвращает 404 непосредственно на запрошенном URL, без Location и без смены адреса браузера на /404. Оформление ошибки может быть общим React-компонентом.
- После замены потребителей удалить из действующих build inputs и репозитория действительно неиспользуемые старые HTML/CSS/JS и page wrappers. Для каждого удаляемого файла указать потребителей, замену и место сохранения материала; подтвердить сохранность текста, формул, задач, решений, anchors и уникальных interactive в новом content.json/React. Если старый body.html ещё является входом converter или нужен для незавершённой сверки, сначала заменить/завершить этот consumer, затем удалять файл.
- Общие media/fonts и ресурсы новых уроков сохранять. Не выполнять массовое удаление curriculum или исходного авторского контента по расширению/названию. После вывода старого файла материал остаётся в новом формате и восстанавливаемой Git-истории; pinned oracle не переносить в target runtime.
- Существующие immutable releases, резервные копии и история публикаций не переписываются и не удаляются произвольно. Они не должны обслуживать обычный публичный запрос старого URL. Их retention/удаление определяется отдельным release/recovery регламентом.
- Приёмка: старый URL отсутствует в активной публичной route/page карте, прямой GET/HEAD даёт 404 без redirect, ответ не содержит старого урока; unknown URL ведёт себя так же. Показ надписи «404» с HTTP 200 или живым старым route/page не принимается. Реальные runtime-проверки выполняются только в согласованном профиле.

### Уборка остатков переноса — решение 18.11.2026

Уборка входит в обязательный результат T011 вместе с выводом старых страниц. До удаления сверить [карту проекта](../../../docs/repository-map.md), реальные imports, build/CLI inputs и ссылки в действующих документах. В существующей карте вывода для каждого файла или однородной группы указать назначение, потребителей, замену/причину удаления и действие. Старое имя или дата сами по себе не доказывают, что файл не нужен.

Убрать подтверждённые остатки переноса:

- Одноразовые конвертеры/скрипты, временные выгрузки, скриншоты, отладочные файлы и резервные копии, если их задача завершена и они больше не нужны для работы или принятой передачи. Повторяемые инструменты оставить с понятным владельцем и командой.
- Дубли компонентов, экспериментальные wrappers/adapters, мёртвые импорты, стили, обработчики и ветви legacy fallback после замены всех потребителей. Удаление legacy HTML/CSS/JS выполняется по правилам сохранности материала выше.
- Ресурсы, созданные только для выведенного интерфейса, если они не используются новыми уроками, общими компонентами или сохраняемыми инструментами. Не удалять media/fonts по одному расширению или папке.
- Устаревшие временные инструкции и повторяющиеся рабочие сводки переноса. Действующие команды, ссылки, указатели curriculum и карта проекта должны описывать оставшуюся структуру. Исторические receipts, ревью и приёмки не переписывать и не удалять как дубли.

Локальные кеши и временные результаты очищать адресно после проверки точного пути и использования процессами. Не выполнять массовые clean/delete для var, static, curriculum или frontend/.cache. Чужие файлы, private config, БД, рабочие окружения, активные releases, планы/журналы восстановления, сохранённые ветки, stash и резервные bundles не считать мусором. Незавершённые или непонятные файлы оставить с конкретным пояснением в той же сводке. Не удалять тесты, guards и assertions только потому, что прогоны сейчас отключены; уборка не превращается в реорганизацию QA, Git-истории или всего репозитория.

Критерий завершения: подтверждённые ненужные остатки удалены, у каждого удаления есть основание, imports/build inputs и действующие ссылки обновлены; необходимые исключения объяснены. Одного списка кандидатов без удаления подтверждённого мусора недостаточно. Фактическую работоспособность оценивать только в согласованном профиле, без новых QA-скриптов и самовольных прогонов.

### Реальный runtime и публикация

Обязательные точки исследования: site_content/material-routes.json и redirects.json, Content route/resolver/build/release inputs, публичный fallback backend/infrastructure/http/app.py, frontend route manifest и public loader, dev proxy, SSG/public artifact и применимые edge rules. Сверить реальные imports и consumers; это список входов, не разрешение переписать всё перечисленное.

Runtime читает pinned immutable Content release. Правка source JSON сама по себе не изменяет установленный release. Подготовка/активация новой редакции — только штатным reviewed Content workflow с явным планом и сохранением guards. Не переписывать immutable release и БД вручную, не запускать публикацию на startup. Публикационный план, изменение локальной БД, сборка и необходимые проверки согласуются по действующим правилам; текст карточки не даёт дополнительного разрешения.

Старый path не должен обслуживаться как 200 через catch-all, public-foundation/body_html или скрытый proxy fallback. Удалить соответствующие legacy redirects из новой действующей редакции, а не только пункт навигации. Не обнулять весь registry redirects без классификации: API, auth, media и технические переходы имеют отдельные контракты. Если existing source/HTTP validation требует старый alias, оформить узкое изменение policy/addendum, не отключать валидатор.

### Приёмка этого пункта

В согласованном профиле отдельно подтвердить:
1. Все 263 новые canonical темы доступны без перехода через старый URL.
2. Из каталога/поиска и соседних уроков ссылки сразу идут на правильную тему с нужным anchor/query.
3. Retired path при прямом GET и HEAD возвращает 404 без Location на урок; SPA-навигация также показывает общую 404 и не восстанавливает старый UI. Проверить неизвестный адрес отдельно. Страница «не найдено» с HTTP 200 не считается выполнением.
4. Нет оставшихся lesson/category alias-цепочек, meta-refresh или JS-переходов со старых учебных URL; sitemap/canonical не рекламируют выведенные страницы.
5. Новые URL корректно работают при reload/Back и в действующем host-dev; результат установленного pinned release учитывается отдельно от HMR.
6. Изображения, формулы, шрифты, ответы авторской самопроверки и существующие API/auth не потеряны. Технические ошибки/503 не маскируются общей 404.
7. Для непроверенного явно указать NOT_RUN_BY_USER_REQUEST/ограничение; source-карта не заменяет runtime receipt.

Новые QA-скрипты, suites, browser automation и массовые прогоны этим перечнем не разрешены. Охват ручного просмотра и команд определить перед отдельно порученной проверкой.

### Известные зависимости, которые нельзя обойти удалением файлов

В базе подготовки e25f302210a91e01364cc637a794704870fbcf31 [load_bundle](../../../backend/content/sources.py) читает body.html/page.css/page.js и для react-v1; publication_digest и compatibility_assets_digest связывают source/публикацию с прежними входами. [Converter](../../../frontend/scripts/convert-lesson.mjs) также читает body.html. Перед реализацией перепроверить актуальный HEAD, затем обновить все действующие потребители удаляемого входа. Не оставлять пустые HTML-заглушки, константные digest, поддельные receipts или широкие fallback ради прохождения guards.

Новая текущая source/publication binding должна проверять реальные bytes нового источника. Не переименовывать версии или менять schema/digest protocol без обоснованного addendum и review; не переписывать frozen fixtures и прошлые manifests/receipts. Если для чтения прежних immutable releases нужен совместимый reader, он не должен снова публиковать старые публичные уроки. Различать retired presentation и сохраняемую Content identity: нельзя снять is_published у общей темы так, что исчезнет новый canonical урок, или удалить её пользовательские связи.

Чтение Git-истории для восстановления исходника — отдельное сравнение, не обязательный запрос обычного runtime. Не тянуть oracle/Django в target и не переписывать учебные content.json только ради подгонки converter. Передача source-комплекта должна оставаться воспроизводимой штатным способом на другом checkout.

### Общая 404 и границы доступа

- Одна общая страница с существующими Brand/header/footer, палитрой и темами; читаемые заголовок и пояснение, переход к материалам и на главную. Не создавать новый визуальный стиль, декорации и отдельный prototype server.
- Прямой запрос HTML получает реальный 404; HEAD имеет тот же статус и headers без тела. При SPA-переходе показывается общий 404 без принудительного изменения URL. У уже загруженного документа HTTP-статус задним числом не меняется: такой просмотр не заменяет проверку прямого запроса.
- Не индексировать страницу ошибки и не оставлять на ней canonical/OG metadata прежнего урока. Содержимое несуществующего slug и server exception не отражать в HTML небезопасным способом.
- До проверки приватного доступа не показывать staff данные/меню. Скрытый staff HTML URL для non-staff не раскрывает существование раздела; API сохраняет предусмотренные контрактом 401/403/404 и JSON envelope. Не заменять все ошибки API или 500/503 страницей 404.
- Отдельный технический отказ, сбой сети и недоступность Content остаются отличимыми от отсутствующей страницы. Не делать бесконечный retry или автоматический переход на главную.

### Что сохраняется без нового обсуждения

Принятые главная с орбитой, каталог с глобальным поиском/выбором класса, lesson renderer и все предметные интерактивы, самостоятельная auth и ЛК сохраняются. Проверить ссылки от сохранённого класса и явных параметров каталога. Черновой radio-выбор не меняет сохранённое предпочтение. Общая публичная шапка/footer переиспользуются без копий и staff redesign.

Существующие авторские вопросы/ответы самопроверки остаются доступны без входа. Blur/LLM gate и новые assessed режимы из N014 здесь не реализуются. Текущие пользователи, пароли, сессии, права и данные не пересоздаются. Не подключать почту, провайдер, XP или будущий прогресс. Отложенные T010/N006/N020 не возвращаются в scope под видом устранения legacy.

При работе с локальным runtime и при передаче результата не добавлять в Git/PR выгрузки пользователей, реальные логины/почту, пароли и их хэши, cookies, токены и private config. Для описания сценариев использовать обезличенные примеры; сохранность данных не подтверждать публикацией самой базы.

## Матрица передачи и критерий завершения

На согласованном candidate различать source review, реальный browser review и installed-release evidence. Для каждой области указать SHA/редакцию, результат и ограничение:

| Область | Ожидаемый результат |
| --- | --- |
| 263 темы всех шести классов | Полнота identity/URL, теории, формул, media, задач/решений и уникальных интерактивов сохранена; mapping уже задан, нового переноса нет |
| Публичная навигация | Главная, каталог, поиск, классы/предметы, соседние темы и информационные страницы ведут на действующие новые адреса |
| Выведенные адреса | Полный список из карты не обслуживается как страница/redirect; прямые GET/HEAD и SPA учитываются раздельно |
| Контент и ресурсы | Ни одного необъяснённого удаления; source loader/build/dev projection больше не требуют удалённых файлов |
| Остатки переноса | Подтверждённые временные файлы, дубли и мёртвый код удалены; imports, команды и ссылки актуальны; защищённые данные и история сохранены |
| Identity и приватность | Вход/выход и безопасный возврат сохранены, guest self-check работает; нет прежних приватных данных после смены пользователя |
| Внешний вид | В согласованном ручном просмотре desktop/узкий экран и обе темы, включая 404; прежние отдельные receipts классов не заменяют общий просмотр |
| Загрузка сайта | Разобрать ранее замеченное замедление по реальным imports/запросам и согласованному наблюдению; исключить лишние legacy fallback и повторную загрузку. Не обещать ускорение без сравнения в одинаковом режиме и не вводить нагрузочный benchmark в эту задачу |
| Поставка | Source SHA/tree, активный release/manifest при его наличии и реальная публикация зафиксированы отдельно; локальный HMR не назван production |

Не требуется заново вручную сравнивать каждую формулу всех 263 тем, если учебные документы не менялись. Полнота структурной карты обязательна; ручной регрессионный просмотр охватывает общие пути, все типы интерактивов и адресно изменённые области по согласованному scope. Если меняется учебная математика, это отдельный дефект/решение с предметным review, а не скрытая часть очистки.

Сначала подготовить весь разрешённый код, карту и PR, затем предъявлять конкретный план активации, если она необходима. Не спрашивать разрешение на каждую CSS-правку или уже согласованное удаление; publisher/schema approval и новые архитектурные решения по-прежнему требуют человека. При блокере остановить только зависимый шаг и продолжить независимую работу. Ограничение scope прогонов не отменяет штатные guards.

Source implementation может быть READY_FOR_REVIEW при отдельно отмеченной pending activation/проверке. Вся T011 не ACCEPTED, пока Руслан не принял объединённую версию. Тестовый PASS, peer review, merge, Content activation и production — разные факты. После передачи не начинать N007 автоматически.

## Что не входит

Доработка админки T010; новый UI kit; переписывание tests/tooling и создание QA-каскада; provider/deploy; новые уроки и будущий учебный цикл. Действующий защищённый минимальный staff может остаться отдельным приватным интерфейсом. Не удалять его API/данные/guards ради требования «нет старого публичного UI».

## Приёмка и проверки

Все 263 темы доступны по новым canonical URL; внутренние ссылки ведут туда напрямую; выведенные учебные адреса дают 404 без старого UI и redirect. Нет оставшихся публичных legacy consumers; сохранены контент, anchors, media и Identity. Source completeness, peer review, общая ручная приёмка, merge и production учитываются раздельно.

Текущая testing-policy приоритетна. Эта редакция карточки не разрешает tests/typecheck/build/browser automation/smoke/full suites. До отдельного поручения: NOT_RUN_BY_USER_REQUEST. Штатные validators/guards не отключать. Исторические receipts не подтверждают новый candidate. Реорганизация QA отложена отдельно, сохранение security/content assertions обязательно.

## Git и завершение

Сохрани чужой dirty tree, данные и private config. Отдельные Issue, ветка от свежего main и PR без дублей; не работать в main и не выполнять merge/deploy автоматически. В карточке/PR одна актуальная сводка: исходный/итоговый SHA, карта выведенных consumers, actual checks и ограничения. Саморевью не заменяет независимое review. После передачи остановиться.
