# Дополнение о платформе и persistence v1.0.2

PROPOSED. Реализует только принятую интерпретацию ADR0006 в терминах framework.
Семантика домена, корневые PRODUCT/ARCHITECTURE/Harness остаются замороженными.

Целевая система — один синхронный Python modular monolith и одна база PostgreSQL16+,
SQLAlchemy2 Session на unit of work, одна проверенная цепочка Alembic;
framework pre-render React/TS/Vite/React Router для публичных routes. Node служит
инструментом сборки. Версии/locks — решения V01/I01; здесь не используются плавающие latest.
Явно включённый SQLite поддерживает только локальную работу без concurrency и никогда
не служит заменой PG или основанием для приёмки locks/upgrade. Текущая запускаемая
реализация остаётся на Django.

## Полное сопоставление baseline

[schema-mapping-v1.json](schema-mapping-v1.json) содержит каждый физический столбец/
constraint/index/applied migration baseline из очищенной инвентаризации PG R01,
а также метаданные каждого model из кода: поля/связи/default/on_delete, включая
автоматически созданные таблицы M2M. Каждый столбец сопоставляется с теми же именами
таблицы и столбца. Перенумерация запрещена: ID content/auth типа integer/bigint и users типа UUID;
сохраняются все unique/check constraints, FK targets, join IDs и storage keys.
Массив sequences в R01 пуст, поэтому он НЕ доказывает отсутствие sequences.
Отдельная проверка sequences выполняется только на одноразовой свежей схеме PG
и определяет GENERATED BY DEFAULT AS IDENTITY и owned sequences. V01 также сравнивает
метаданные и значения sequences в развёрнутой копии.

SQL-типы: UUID -> native uuid; JSONField -> jsonb с явным различением JSON null и
SQL NULL; DateTimeField -> timestamptz с точностью до микросекунд; PositiveInteger/SmallInteger
-> integer/smallint с проверкой >=0; Boolean -> строгий bool; Char/Slug/FileField
-> существующая длина varchar; Text -> text. ID Auth User/Group/Permission — int4;
content и автоматически созданные M2M ID — int8. FileField означает storage key,
а не встроенный медиафайл. Автоматическая смена пути, escaping, перевод в нижний регистр
или Unicode normalization запрещены.

Python/model defaults обычно являются application defaults, а не SQL defaults.
auto_now_add назначает UTC при insert; auto_now — только при save с включённым этим полем
(поведение update_fields/bulk QuerySet.update должно совпадать). Publish меняет
updated_at/published_at только при соответствующей принятой записи. Существующие
моменты времени/точность сохраняются; их нельзя заменять временем выполнения migration.
uuid4 генерируется только для новых строк. Пустой текст по умолчанию — пустая строка;
nullable grade/mode/receipt остаются NULL. Legacy epoch Grade —
`2026-10-04T00:00:00Z`, это epoch отслеживания, а не восстановленная историческая дата создания.
Заполняются только недостающие profiles; выбранные значения grade/mode/state существующих
пользователей не меняются.

Физические Django FK обычно отложенные NO ACTION. Django on_delete задаёт поведение
collector/service, но не означает SQL ON DELETE CASCADE. Физические constraint/deferability
сохраняются, а целевые services реализуют поведение, эквивалентное collector:
Subject.grade и Section.subject CASCADE; grade/subject/section страницы SET_NULL;
publication.page CASCADE; media.related_page SET_NULL; profiles.user/grade и
receipt.user PROTECT; auth joins/admin log — по mapping. Все блокирующие PROTECT
зависимости проверяются до любого удаления. Пассивный ORM cascade не может обойти
защиту пользователя при bulk/delete-selected. Model choices не являются DB CHECK,
если mapping не указывает реальный constraint; application validation сохраняется.

Сохраняются владелец/тип/increment/min/max/cycle/cache PK sequence; sequence нельзя
перематывать назад. После копирования следующий сгенерированный ID должен быть выше
максимального существующего. Используются проверенные правила setval с учётом is_called,
пустой таблицы и уже большего last_value. Это репетиция V01, а не SQL, выполняемый в R02.
История django_migrations/admin/session/contenttype сохраняется; DROP не требуется.
Стабильны permission IDs/codenames/contenttypes и назначения M2M, включая users models
без зарегистрированного admin. Новые target sessions/journal/bridge tables требуют
проверенного additive DDL в V01; R02 их не создаёт.

## Upgrade и владение

V01 охватывает одноразовые профили: A — content0001 без users и timestamp Grade;
B — полный baseline с текущей цепочкой; C — заполненные users/profiles/roles/receipts
и ожидающие requests. Перед upgrade создаются архивная backup и digest schema.
До и после проверяются строки/ID/FK/constraints/timestamps/sequence/hash algorithms,
а также следующий insert и защищённое удаление. Fresh Alembic создаёт схему с нуля,
а bootstrap дважды не может перезаписать identities/evidence; свежие 279 pages
в сравнении с legacy 281/279published объясняются сохранением unpublished materialy/pamyatki.
Нельзя делать stamp до эквивалентности схемы, репетиции и независимого человеческого ревью.

Владимир — единственный владелец, имеющий право записи в Alembic. До cutover Django
владеет DDL и всеми записями Content/Users. Production shadow target доступен только для чтения;
записи/тесты разрешены только в disposable окружении. Cutover: остановить API/CLI/admin/
текущие publishers, отозвать права legacy writer, проверить отсутствие старых writers,
переключить все domain routes/CLI/admin на target и только затем разрешить записи target.
Одновременный запуск migration/writer запрещён. После записей в target rollback требует
согласования формата/receipts/assets; если legacy не может читать новые записи, предпочтителен
forward repair. R02 не меняет базу данных.

## Общий протокол транзакций и locks

Все новые target services захватывают только нужные locks в следующем общем порядке:
1. gate активации publication (только для записей publication/catalogue);
2. advisory locks namespaces, упорядоченные по (domain, stable scope), включая создание
   и гонки unique-key;
3. существующие строки User по возрастанию PK;
4. строки Group, auth membership/direct/group-permission joins по возрастанию PK,
   затем IdentityReceipt по (scope,operation,key_digest);
5. строки StudentProfile по возрастанию user_id;
6. Grade, Subject, Section по rank таблицы/PK;
7. ContentPage по PK, затем LessonPublication по page_id;
8. MediaAsset, затем Redirect по PK;
9. строка journal/указатель active.
При объединении операций порядок нельзя менять; service, которому пришлось бы его нарушить,
перезапускается на внешней orchestration boundary. LoginWindow — независимая короткая
транзакция с ограниченным бюджетом до проверки credentials, она никогда не удерживается
вместе с другими locks.
Replay регистрации может прочитать receipt без lock только для определения предполагаемого user,
затем захватывает User -> receipt и повторно проверяет каждый digest/owner fact. Новая регистрация
не имеет существующего User lock и вставляет user/profile под scope lock/unique receipt.
Onboarding: User -> receipt -> profile. Bulk действия staff блокируют users/joins в отсортированном
порядке и проверяют все PROTECT-блокировки до изменений. Рендеринг файлов, сеть и вызов LLM
не выполняются под DB row locks. Unique constraints остаются последней защитой от гонок;
nested savepoints обрабатывают duplicate inserts, нельзя продолжать прерванную транзакцию.
Повторы deadlock/serialization ограничены по числу и сохраняют key/body; при исчерпании
возвращается безопасный 503.

Будущие locks Assessment/Progress — обязательства adapters, а не реализованные таблицы:
owner/version exposure -> attempt -> постоянная identity действия -> guard положительного credit
-> проекция Progress user/skill в отсортированном scope. Replay receipt выполняется до проверок
revision/state; immutable event/completion dual identities глобальны, а не скрыты в owner partitions.
Assessment выдаёт DTO, только Progress меняет проекцию. До появления этих будущих доменов
канонический порядок захвата нужно пересмотреть; текущая миграция их не реализует.

## Решения по ревью

Одобрить additive namespace delivery/staff и контракты locks/bridge на этой точной ревизии R02.
Реализация V01 должна добавить сведения о schema/sequence конкретного развёртывания;
V03 должна доказать совместимость password/session signer. Неподдерживаемый legacy algorithm/key
или недоказуемый replay bridge блокирует cutover; нельзя обходить это сбросом пароля,
удалением receipt или выдуманным одобрением.

## P1 Авторитетное durable состояние publication (предложенная ревизия 1.0.2)

Gate publication — ОДИН долговечный singleton PostgreSQL на публичный release namespace
развёртывания, а не process mutex, время жизни worker или transaction advisory lock.
Вся публикация/unpublish/bootstrap и записи, меняющие catalogue, должны проходить через этот
механизм. Pending slot захватывается ДО VALIDATED/staging и остаётся занятым до DB_COMMITTED,
activation, recovery и публичной проверки. Истечение lease не освобождает slot. Gate ранга 1
представляет собой короткую блокировку этой строки singleton; journal ранга 9 следует после
domain rows. Rendering, загрузка файлов, очистка cache и сетевые health checks выполняются
вне DB locks.

Долговечные факты и writers описаны в [protocol mapping](protocol-storage-mapping-v1.json).
PostgreSQL хранит gate (pending operation ID, текущий непрозрачный worker owner ID,
строго возрастающее int64 поколение fence, lease_until), journal (неизменяемые plan/key identity,
фазы, факт DB commit и результат activation), DB edition и единственный авторитетный active descriptor
(operation ID, release ID, digest manifest, поколение fence). Tuple владения journal должен
совпадать с pending slot, пока операция не терминальна. Content publisher/recovery service —
единственный domain writer; продвигать операцию может только владелец текущего lease. V01
проверяет additive DDL/constraints; V04 реализует протокол; V05 — gateway, закрепляющий этот
descriptor для каждого request. В R02 новая инфраструктура, таблицы или runtime не создаются.

Неизменяемые staged files содержат только точные manifest/page/assets; сами по себе они
не дают полномочий. Второй изменяемый указатель filesystem symlink/proxy-config отсутствует.
Activation в одной короткой транзакции под gate меняет PostgreSQL descriptor и факт activation
в journal после проверки долговечных staged hashes. Gateway читает этот descriptor и отдаёт только
соответствующий immutable release; он не должен брать свежие поля ContentPage для старого активного
HTML. После завершённой проверки gateway cache не может самостоятельно выбрать старый release.
Если такую схему нельзя реализовать, развёртывание блокируется до явного ревью альтернативы;
проверить fence, а затем переименовать symlink недостаточно. Здесь задано предложенное
представление activation, оставленное открытым ADR0006; совместная транзакция DB/filesystem
не подразумевается.

Каждая команда, меняющая состояние, передаёт (operation_id, owner_id, fence_generation)
и после захвата gate повторно проверяет равенство pending и `lease_until > PostgreSQL clock_timestamp()`.
DB commit, renew, обновления phase/result, activation, terminal release и очистка staging требуют
этой проверки в точке commit. Поколение назначает gate, а не worker; оно увеличивается при
первичном claim и takeover, не сбрасывается и не используется повторно (в том числе между
операциями). Переполнение закрывает операцию безопасно. Команды старого поколения возвращают
FENCED, даже если позднее вернулся тот же worker ID. Они не могут подтвердить content,
переключить active, очистить pending, подтвердить health или удалить сохранённые файлы.
Результаты выполнявшихся build/probe принимаются только с той же текущей tuple и release/digest.
Staging использует immutable files с проверкой digest и временные корни, отдельные для поколения;
запоздалая старая загрузка не может перезаписать готовый manifest. Purge ограничивается
идемпотентной инвалидацией привязанных release/paths; stale workers не могут начинать новые эффекты,
а уже отправленный purge не выбирает release и не подтверждает успех. Долгая сетевой lease не заменяет fencing.

Renew разрешён только для текущего неистёкшего lease; просроченный владелец должен запросить
recovery, даже если другой worker ещё не появился. Recovery workers читают pending, затем
выполняют CAS ожидаемой operation/generation под gate после expiry или после явной передачи
полномочий текущим владельцем. Победитель увеличивает generation, связывает его со своим owner
и новым lease и в той же транзакции записывает tuple в journal. Проигравшие получают OWNER_BUSY
(lease активен) или CLAIM_CONFLICT (наблюдавшееся generation изменилось), перечитывают состояние
и останавливаются; новую operation они не создают. Повторный точный claim с новым текущим token
возвращает OWNED без увеличения; это read-only проверка token/lease, а не новый takeover.
Повтор с устаревшим expected generation остаётся конфликтом. Длительность lease — положительный
параметр deployment, записываемый V04; источник времени — DB, потеря соединения с DB не продлевает
владение локально.

Service может читать/согласовывать состояние без владения, но сохранять результат может только
владелец claim. Committed plan pending operation неизменяем: recovery не может менять следующий
release/source/body/key или повторять domain DB mutation. Только FAILED_PRECOMMIT
(проверено отсутствие domain commit и activation) или COMPLETE (совпадают active descriptor,
DB edition и успешная публичная проверка/purge именно этого release) атомарно очищают pending.
Следующая publication требует pending NULL, проверенных active==DB edition, нового generation и
повторной проверки ожидаемых active/source digests вызывающего. DB commit/recovery, истечение lease,
UNKNOWN activation и ошибка health/cache блокируют следующую публикацию. Неустранимая порча после commit
оставляет gate занятым и завершает операцию безопасно; rollback/abandonment после commit требует
отдельного конкретного решения человека о восстановлении, а не автоматического освобождения gate
или новой operation.

Takeover после commit записывает RECOVERY_REQUIRED/OWNER_LOST, сохраняя факты db_committed и
activation; до нового намерения activation требуется reconciliation. Takeover до commit сохраняет
VALIDATED/STAGED. Первичная раздача target требует проверенных initial descriptor/DB edition;
отсутствующий initial descriptor означает недоступность и никогда не разрешает произвольную первую публикацию.

Validity lease проверяется защищённой авторитетной SQL mutation по времени DB при заблокированной
строке gate; это точка линеаризации перехода. Подтверждение COMMIT транзакции может прийти позже.
Takeover не может вклиниться в транзакцию: он ждёт ту же строку gate, перечитывает новый
committed descriptor/journal, затем выделяет следующее generation. Предварительная проверка
времени вне этой блокировки не даёт полномочий. Если lease уже истёк к моменту защищённой mutation,
запись отклоняется, даже если другого worker нет.
