# Инструкция координатору миграции MathStart

Статус пакета: PREPARED_NOT_STARTED. Наличие этих файлов не запускает миграцию.
Применять пакет после явного стартового поручения пользователя.

## 1. Цель и точный объём

В существующей ветке `ms7-mig-react-fastapi` довести до технической готовности
все оставшиеся задачи **MS7-MIG-R03–R06, V03–V06, I02–I06**. Сохранить результаты
**MS7-MIG-R01, R02, V01, V02, I01**. Эти обозначения в пакете всегда относятся
к программе MS7-MIG, а не к одноимённым задачам основного продукта.

Результат: воспроизводимая текущая версия MathStart на FastAPI и React,
проверенная на одном итоговом коммите, с данными, контентом, административными
операциями, публикацией, документацией, восстановлением и пакетом приёмки.
Обычные startup/API/auth/publisher/migrations/target verification не требуют
Django или DRF. Исторический код и отдельные окружения сравнения сохраняются.

Это перенос существующего поведения. Не реализовывать новые Knowledge,
Assessment, Progress, Solution Analyzer, AI Tutor, Adaptive Practice,
диагностику, assessed exercise runtime или live Product AI. Не закрывать
Product G1–G5. Существующие pure contracts и fixtures остаются обязательными.

## 3. Пользовательское дополнение к процессу

Следующие изменения согласованы пользователем при подготовке пакета и вступают
в действие при его явном запуске. Это дополнение к **порядку исполнения** ТЗ;
исходное ТЗ, frozen schemas, domain semantics и исторические доказательства
не переписываются.

- Выполнить техническую работу всех трёх прежних очередей одной командой агентов.
  Персональные авторы, прежние очереди и календарные сроки не ограничивают запуск.
  Использовать технические роли и реальные зависимости. Не назначать сроков
  и не обещать завершение за фиксированное число дней. Время реальных проверок
  сохранять для воспроизводимости; это не дедлайны.
- V04 и I02 считать **не начатыми** и реализовать с нуля от принятого baseline.
  Не ждать локальный I02, consumer `47baaa9…` или передачу от прежнего исполнителя.
  Не импортировать их незавершённый код автоматически и не удалять чужие ветки.
  При наличии новых принятых результатов на GitHub сохранить их и согласовать
  конфликт с этим исходным условием, а не молча откатывать integration.
- R03 продолжить из существующей незавершённой ветки после контролируемого intake.
  Остальные незавершённые задачи выполнить полностью по их карточкам.
- Для продолжения зависимой технической работы внутри migration-ветки достаточно
  проверенного кандидата и отдельного агентного ревью применимого интерфейса.
  Старые требования получить персональные промежуточные approvals заменяются
  этим процессом **только для нового выполнения**, включая кандидатную интеграцию.
  Существующие принятия сохраняются. `TECHNICALLY_VERIFIED` не переименовывать
  в историческое `ACCEPTED_INTEGRATION`.
- Итоговую человеческую приёмку нового результата выполняет пользователь.
  Не создавать approvals от других людей, не подделывать receipts и не
  переносить старый approval на новый код. Если прежний executable guard
  требует старую персональную процедуру, добавить отдельно версионированный
  режим нового процесса с проверками. Не заполнять его фиктивными review IDs
  и не ослаблять сохранность источников, контрактов или фактических тестов.
- Финальный merge в `main`, закрытие migration Issues, публичный deployment
  и переключение рабочей БД выполняются после отдельного решения пользователя.
  До этого довести технический результат до `READY_FOR_HUMAN_ACCEPTANCE`.
  В R06 явно разделить подготовленный release и ещё не выполненный main cutover.

При платформенном противоречии ADR-0006 и migration contracts заменяют
платформенную часть ADR-0001. Domain/evidence/security invariants остаются.
Этот пакет не даёт разрешения менять публичную семантику, исключать admin
операции, раскрывать ответы или упрощать протокол ради зелёных проверок.
Новый существенный технический выбор за пределами принятых контрактов требует
конкретного предложения и архитектурного решения пользователя.

   после проверки divergence и занятости другим worktree.
3. Пакет пока создан локально и может отсутствовать в remote. До смены каталога

4. Единственная постоянная ветка результата — `ms7-mig-react-fastapi`.
   Временные ветки/каталоги разрешены для изоляции задач, например
   `ms7-mig-v03-identity`, `ms7-mig-v04-publishing`, `ms7-mig-i02-pages`.

5. Один координатор меняет integration refs и общие документы/CI. Без force-push,

   Читать исходники из immutable Git объекта или отдельного checkout; чужой

## 5. Архитектура и обязательные ограничения

- Один модульный Python-монолит, PostgreSQL 16+, Python 3.12+, FastAPI/Pydantic,
  SQLAlchemy 2/psycopg/Alembic/Uvicorn; совместимые lock-файлы. Использовать уже
  принятые версии и границы окружений. Не выполнять произвольный upgrade latest.
- React/TypeScript, Vite/React Router framework mode, существующие CSS/tokens.
  Публичный HTML генерируется по полному manifest; Node нужен для build/publish,
  постоянный Node SSR server не добавляется. Private account/staff не экспортируют
  персональные данные в SSG и имеют no-store. Один origin для UI и API.
- Не добавлять редизайн, глобальный reset, Tailwind, MUI, shadcn, Motion,
  Redis, Celery, микросервисы, новую CMS или массовое преобразование уроков в JSX.
  Новую зависимость вводить только с обоснованием внутри назначенной задачи.
- Сохранить authored HTML, формулы, SVG, anchors, локальные и общие CSS/JS,
  content/source IDs, storage keys, slug identity, URL/redirect/404/SEO.
  Вставлять только publisher-reviewed HTML; пользовательские и LLM строки
  экранировать. Секреты проверки не включать в HTML/JSON/JS/fixtures build.
- Сохранить канонические HTTP contracts, exact JSON integers/IDs, strict input,
  errors/statuses/trailing slashes/cursors. Автоматический OpenAPI FastAPI
  не заменяет frozen OpenAPI. Планируемый endpoint не реализуется заглушкой 200.
- Сохранить session cookies/CSRF/Origin/Host, password hash compatibility,
  receipts/replay/owner binding/rates, все зарегистрированные staff операции.
  JWT и credentials в browser storage не вводить. Onboarding сохраняет выбор,
  а не запускает новые домены. React не рассчитывает authoritative прогресс.
- Короткие транзакции, Session на единицу работы. Одна техническая роль владеет
  Alembic и DDL. Не допускать совместных live writers Django/FastAPI или
  одновременного DDL Django/Alembic на общих таблицах. До разрешённого cutover
  все изменяющие проверки — на явно disposable данных.
- Сохранить IDs/UUIDs/FK/CHECK/UNIQUE/sequences/defaults/timestamps, profiles,
  roles/permissions/password hashes и receipts. Applied migrations не править;
  schema corrections делать additive. SQLite opt-in допустим для разработки,
  но не является доказательством PostgreSQL concurrency/upgrade.
- DB commit и активация файлов/SSG — разные ресурсы. Реализовать принятые journal,
  durable pending gate, fencing/takeover/recovery и coherent release activation.
  Bootstrap не перезаписывает исторические evidence или runtime edits.
- Content владеет topic-to-skill mappings и зависит от Knowledge. Только Progress
  изменяет долгосрочное состояние через validated evidence. Четыре exercise modes,
  typed ordered steps, raw/normalized, hint/reveal, secrecy, graph DAG и LLM trust
  сохраняются как контракты; будущие домены остаются planned.

## 6. Организация агентов

При наличии инструмента делегирования использовать координатора и максимум
доступных специализированных агентов. Не создавать новые пользовательские чаты
как замену субагентам. Не задавать новую модель/усилие/бюджет без запроса.

| Роль | Работа | Исключительное владение |
| --- | --- | --- |
| Координатор | R03, R05, R06; зависимости, evidence, интеграция и процесс R04 | root scripts/CI/Harness, текущая документация, integration refs, STATE |
| Backend | V03–V06, отдельные необходимые fixes V01/V02 | backend services/API, Alembic/schema, backend locks, операционные конфигурации |
| Frontend | I02–I06, обязательные I01 follow-ups | frontend routes/components/CSS/lifecycle, frontend lock и browser tests |
| Рецензент | Отдельное review increments и R04 audit | read-only code review; findings/review records по согласованной области |

Профили: [backend](docs/migration-agents/backend.md),
[frontend](docs/migration-agents/frontend.md),
[reviewer](docs/migration-agents/reviewer.md).
Координатор сам проверяет результаты; рецензент не подменяет исполнителя.
Если субагенты недоступны, продолжать implementation последовательно, фиксируя
ограничение. Не заявлять независимое агентное ревью без отдельного reviewer
context; незакрытое требование review остаётся в готовности финального пакета.

Каждое поручение содержит task/slice ID, exact input SHA, каталог, writable paths,
контракты, зависимости, тесты, ожидаемый deliverable и stop conditions.
Перед началом разделить ports, DB names, runtime/report roots. Не использовать
чужие среды из старого `tmp/`. При конфликте областей координатор передаёт patch
владельцу; одновременная запись нескольких агентов в файл запрещена.

## 8. Документация, автономность и завершение

R05 входит в миграцию: полноценная новая редакция основного ТЗ, changelog,
source hashes, все 52 product task IDs, platform disposition и §17 links.
Новые рабочие migration-инструкции не содержат персональных исполнителей
и дедлайнов. Старые календарные данные — только исторический источник;
новые сроки/обязательства основной программы не назначать. Её организационные
решения и роли не переписывать под видом технического переноса.

Основной `AGENTS.md` не менять при bootstrap пакета. В завершающей R05 разрешена
его scoped адаптация к реально полученной платформе вместе с PRODUCT,
ARCHITECTURE, README, verification/runbooks/templates. Сначала сохранить
существующие пользовательские изменения; не переносить их из исходного checkout
автоматически. Не редактировать frozen документы массовой заменой названий.

R05 читает полный исходный v7.1, а не восстанавливает его по краткому migration
addendum. Путь и исходный hash указаны в STATE. Если источник недоступен,
продолжать независимую реализацию, а конкретную документальную зависимость
обозначить BLOCKED. Не придумывать недостающие 52 карточки.

Устанавливать совместимые инструменты и запускать изолированные проверки
в пределах явного execution-поручения. Реальные системные permissions уважать;
не отключать защиту и не менять working/production DB ради прохождения checks.
При блокере записать точную причину/команду/нужный вход и продолжать независимые
задачи. Не повторять неизменный failing pipeline без нового входа или исправления.

Перед исчерпанием контекста или завершением сеанса обновить STATE: committed SHA,
dirty paths, роли/каталоги, checks, findings, следующий доступный шаг. Не обещать
самопроизвольное продолжение после закрытия приложения. Следующий запуск читает
STATE и проверяет факты повторно.

Техническая финишная точка — все 13 задач технически проверены, общая матрица
прошла, blocking findings отсутствуют, release/runbooks/docs/rollback готовы,
draft final PR и CI привязаны к итоговому SHA. Статус:
`READY_FOR_HUMAN_ACCEPTANCE`, не `MIG-G4 COMPLETE`.
Подготовить одну конкретную передачу пользователю: что работает, как запустить,
что проверено, где release/diff/evidence и какие финальные действия ожидают
решения. Формальные main merge/Issue closure/deployment остаются явно pending
до действительного выполнения и проверки соответствующих результатов.
